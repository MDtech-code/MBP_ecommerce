# MBP E-Commerce API Communication Standards

## 1. The Universal JSON Envelope
To guarantee consistency across the entire project, every HTTP endpoint — regardless of whether it succeeds or fails — must return a standardized JSON envelope. Neither frontend components nor backend views should ever transmit raw, unwrapped arrays or primitives.

### The 5-Key Envelope Schema
```json
{
  "success": true,
  "message": "Resource retrieved successfully",
  "data": { ... },
  "errors": null,
  "meta": {
    "request_id": "req_01H8X9A2B3C4D5E6F7G8H9J0K1"
  }
}
```

| Field | Type | Description |
|---|---|---|
| **`success`** | `boolean` | `true` for HTTP status codes `200–299`, `false` otherwise. |
| **`message`** | `string \| null` | A human-readable summary suitable for displaying in UI toasts or alerts. |
| **`data`** | `any \| null` | The primary response payload. Always `null` when `success` is `false`. |
| **`errors`** | `any \| null` | Detailed error breakdowns (field validation maps, error codes). Always `null` when `success` is `true`. |
| **`meta`** | `object \| null` | Cross-cutting metadata including pagination cursors and tracing timestamps. **Always contains `request_id`**. |

## 2. Backend Enforcement (Django REST Framework)
The backend enforces this envelope at two levels: view inheritance for successful responses, and a global exception handler for errors.

### View Layer: `BaseAPIView`
All API views **must** inherit from `apps.core.api.views.BaseAPIView`. Direct use of DRF's `APIView` or `GenericAPIView` is strictly prohibited. 

`BaseAPIView` delegates to `APIResponseMixin` and overrides `transform_payload()` to automatically inject the unique `request_id` generated by middleware into the `meta` block.

#### Standard Response Helpers
Views should use the semantic built-in methods rather than constructing dictionaries manually:
* **`self.success_response(data=..., message=...)`**: Returns `200 OK`.
* **`self.created_response(data=..., message=...)`**: Returns `201 Created`.
* **`self.error_response(errors=..., message=..., status_code=...)`**: Returns custom `4xx` client errors.
* **`self.unauthorized_response(message=...)`**: Returns `401 Unauthorized`.
* **`self.forbidden_response(message=...)`**: Returns `403 Forbidden`.
* **`self.not_found_response(message=...)`**: Returns `404 Not Found`.

### Global Error Handling: `custom_exception_handler`
All raised exceptions and validation failures pass through `apps.core.api.exceptions.custom_exception_handler`. This ensures that even unexpected system crashes maintain envelope parity.
* **Error Normalization (`_format_errors`)**: DRF often returns mixed structures (single strings, lists, or nested dicts). The handler unwraps single-item error lists into plain strings so the frontend can display them directly without array indexing.
* **Security & Leak Prevention**: For unhandled `5xx` server exceptions, raw tracebacks are **never exposed to the client in production**. The response cleanly returns `"An unexpected error occurred"` while alerting registered monitoring systems (e.g., Sentry) and logging the full stack trace internally with the correlating `request_id`.

## 3. Frontend Consumption (React & Axios)
To prevent UI components from manually parsing HTTP envelopes or checking status codes, the frontend uses an abstraction layer via `src/api/transformers.js`. Components deal strictly with domain data or normalized errors.

### Successful Response Unwrapping (`extractResponse`)
When an API call succeeds, the service layer wraps the Axios response in `extractResponse()`. This strips away the Axios HTTP headers and returns only the core payload:
```javascript
// What the UI component receives:
{ data: { id: 1, name: "Product" }, message: "Success", meta: { request_id: "..." } }
```

### Error Normalization (`normalizeError`)
When an API request fails (network drop, `4xx` validation, or `5xx` server crash), the error is passed through `normalizeError()`. This transforms chaotic network exceptions into a predictable `NormalizedError` object.

#### Key Boolean Flags for UI Logic
Instead of writing complex HTTP status checks in UI React hooks, components consume pre-computed boolean flags:

| Flag | Trigger Condition | Intended UI Action |
|---|---|---|
| **`isNetworkError`** | No response received from server | Show "Check internet connection" banner. |
| **`isAuthError`** | HTTP Status `401` | Trigger token refresh or redirect to `/login`. |
| **`isForbidden`** | HTTP Status `403` | Show "Access Denied" screen or hide restricted buttons. |
| **`isNotFound`** | HTTP Status `404` | Render 404 fallback component. |
| **`isRateLimit`** | HTTP Status `429` | Disable submit button and trigger countdown timer. |
| **`isServerError`** | HTTP Status `500+` | Show generic fallback toast; log `requestId` for support. |

## 4. End-to-End Lifecycle Examples

### Example A: Successful Product Creation (`201 Created`)
**Backend View Implementation:**
```python
def post(self, request, *args, **kwargs):
    serializer = self.get_serializer(data=request.data)
    serializer.is_valid(raise_exception=True)
    product = serializer.save()
    return self.created_response(
        data=serializer.data,
        message="Product published successfully"
    )
```

**Wire JSON Payload:**
```json
{
  "success": true,
  "message": "Product published successfully",
  "data": { "id": 104, "title": "Mechanical Keyboard", "price": "120.00" },
  "errors": null,
  "meta": { "request_id": "req_8823f00a91" }
}
```

### Example B: Form Validation Failure (`400 Bad Request`)
**Wire JSON Payload (Normalized automatically by exception handler):**
```json
{
  "success": false,
  "message": "Invalid request data.",
  "data": null,
  "errors": {
    "email": "Enter a valid email address.",
    "password": "Password must be at least 8 characters long."
  },
  "meta": { "request_id": "req_9942b11c02" }
}
```

**Frontend Hook Consumption:**
```javascript
try {
  await loginService(credentials);
} catch (err) {
  const normalized = normalizeError(err);
  // Easily map normalized.errors directly to form field error states
  setFormErrors(normalized.errors); 
  toast.error(normalized.message);
}
```
